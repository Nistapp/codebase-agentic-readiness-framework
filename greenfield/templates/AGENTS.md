> **Template Version:** 2.1.0
> **Purpose:** This file tells AI coding agents how to work in **[Project Name]**. It holds only what an agent
> cannot infer from the code: the commands, the boundaries, the rules for documents and releases, and the
> prohibitions. Keep it that way: no overview, no tech-stack table, no rule a linter already enforces. Keep it
> under 400 lines.

`@AGENTS.md`.

## 1. Commands

1.1 These seven verbs are the only sanctioned way to verify work. CI runs the same script names. Do not invent
ad-hoc invocations (`npx vitest`, `tsc file.ts`) and do not run a check that CI does not run.

```bash
npm run format        # format: rewrite formatting in place
npm run format:check  # format:check: read-only, formatting and lint rules
npm run lint          # lint: read-only
npm run typecheck     # typecheck: tsc --noEmit for src/ and test/
npm test              # test: the full suite
npm run check         # check: THE gate (format:check, typecheck, test)
npm run security      # security: dependency-CVE gate
```

1.2 Run one test, not the suite:

```bash
npx vitest run -t '<test name>'
```

1.3 Node.js `<node-version>` is pinned in `.nvmrc`. The package is ESM (`"type": "module"`).

1.4 Local imports end in `.js` (`"module": "nodenext"` in `tsconfig.json`); the compiler does not add it.

1.5 Run `npm run check` before every commit and pull request. If you cannot make it pass, report the blocker.

1.6 If a code index is registered for this repository, query it before you read whole files.

## 2. Boundaries

2.1 `src/core/` holds pure logic. It never imports from `src/infrastructure/` or `src/cli/`, and never reads
`process.env`.

2.2 Every dependency-injection interface lives in `src/core/interfaces.ts`.

2.3 Filesystem, git and OS operations go in `src/infrastructure/` and implement an interface from
`src/core/interfaces.ts`.

2.4 `src/cli/` is the composition root. It reads `process.env` and wires the dependencies.

2.5 `dist/` is generated by `npm run build`. Never edit it.

2.6 Files are `kebab-case.ts`. Interfaces start with `I` (`IFileSystem`). Test doubles end in `Stub` or `Mock`.

## 3. Documentation

3.1 `docs/` is the single source of truth for permanent documentation. `docs/architecture/README.md` indexes it
and the decisions.

3.2 Every Markdown file under `docs/` and at the root follows `docs/STYLE_GUIDE.md`; never restate its rules.
That covers `README.md`, `CONTRIBUTING.md` and this file. Link to the rules instead.

3.3 Each rule has one home. `docs/STYLE_GUIDE.md` §10 names the home of each topic. Other files link to the home
instead of copying the rule.

3.4 Decisions are ADRs in `docs/architecture/adrs/`. Every ADR you add, change or delete follows
`docs/ADR_POLICY.md`.

3.5 Domain terms are defined once, in `docs/architecture/glossary.md`.

3.6 `artefacts/` is scratch: plans, notes, work in progress. Its contents are git-ignored and kept out of the code
index. It is never a source of truth, and you read it only when a human gives you a file path.

3.7 **Definition of done:** when a change alters a public interface, observable behaviour, the architecture or a
decision, update the affected documentation and the decision records in the same change set.

## 4. Branches and releases

4.1 Branch from `dev` as `<type>/<topic>` and open pull requests into `dev`. `main` receives releases only, through
a pull request from `dev`.

4.2 release-please (`.github/workflows/release-and-sync.yml`) cuts each release from `main`. The steps are in
`RELEASE_PROCESS.md`.

4.3 An agent pushes its branch or opens a pull request only when the owner asks. It never merges, tags or
publishes a release.

4.4 Commit messages follow Conventional Commits (`<type>(<scope>): <description>`); `.husky/commit-msg` runs
commitlint on each one. The workflow for people is in `CONTRIBUTING.md`.

## 5. How to write for people

5.1 These rules apply to chat replies, plans, reports, commit messages, pull request descriptions and docs.

5.2 **Reader:** write for a new engineer who knows TypeScript and Node, but not this repository or its terms.

5.3 **Bottom line first:** put the answer, the result or the decision you need in the first two lines.

5.4 **Plain language:** short sentences (at most 25 words), active voice, one term per meaning.

5.5 **Form:** choose the form from the content: numbered rules, tables, diagrams or alerts
(`docs/STYLE_GUIDE.md` §3.1).

5.6 **Reports:** a status report says what is done, not done, blocked and next. A done report says what changed,
how it was checked and what was not done.

5.7 **Decisions:** give the context, two to four options with pros and cons, your recommendation and the default.

## 6. Never

6.1 Never open, print, log or commit `.env` or any other secret store. Secrets go in `.env`; the variable names go
in `.env.example`.

6.2 Never commit or push to `main` or `dev`.

6.3 Never edit `.github/workflows/` unless the task asks for it.

6.4 Never skip, delete or weaken a test or a lint rule to get a gate green.

6.5 Never ship a public method without a positive and a negative test.

6.6 Never let a unit test touch the real filesystem, git or network. Inject a typed stub; do not mock whole
modules.

6.7 Never verify work with an ad-hoc command. Use the seven verbs in section 1.

6.8 Never add a runtime dependency without an ADR that records the decision.

6.9 Never describe a planned feature as if it exists.
