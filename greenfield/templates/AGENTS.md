## 1. Commands

These seven verbs are the only sanctioned way to verify work. CI runs the same script names. Do not invent
ad-hoc invocations (`npx vitest`, `tsc file.ts`) and do not run a check that CI does not run.

```bash
npm run format        # format: rewrite formatting in place
npm run format:check  # format:check: read-only, formatting and lint rules
npm run lint          # lint: read-only
npm run typecheck     # typecheck: tsc --noEmit for src/ and test/
npm test              # test: the full suite
npm run check         # check: THE gate (format:check, typecheck, test)
npm run security      # security: dependency-CVE gate
```

Run one test, not the suite:

```bash
npx vitest run -t '<test name>'
```

- Node.js `<node-version>` is pinned in `.nvmrc`. The package is ESM (`"type": "module"`).
- Local imports end in `.js` (`"module": "nodenext"` in `tsconfig.json`); the compiler does not add it.
- Run `npm run check` before every commit and pull request. If you cannot make it pass, report the blocker.
- If a code index is registered for this repository, query it before you read whole files.

## 2. Boundaries

- `src/core/` holds pure logic. It never imports from `src/infrastructure/` or `src/cli/`, and never reads
  `process.env`.
- Every dependency-injection interface lives in `src/core/interfaces.ts`.
- Filesystem, git and OS operations go in `src/infrastructure/` and implement an interface from
  `src/core/interfaces.ts`.
- `src/cli/` is the composition root. It reads `process.env` and wires the dependencies.
- `dist/` is generated by `npm run build`. Never edit it.
- Files are `kebab-case.ts`. Interfaces start with `I` (`IFileSystem`). Test doubles end in `Stub` or `Mock`.

## 3. Documentation

- `docs/` is the single source of truth for permanent documentation. `docs/architecture/README.md` indexes it and
  the decisions.
- Every `.md` file under `docs/` follows `docs/STYLE_GUIDE.md`. Link to its rules; never restate them here.
- Decisions are ADRs in `docs/architecture/adrs/`. Every ADR you add, change or delete follows `docs/ADR_POLICY.md`.
- Domain terms are defined once, in `docs/architecture/glossary.md`.
- `artefacts/` is scratch: plans, notes, work in progress. Its contents are git-ignored and kept out of the code
  index. It is never a source of truth, and you read it only when a human gives you a file path.
- **Definition of done:** when a change alters a public interface, observable behaviour, the architecture or a
  decision, update the affected documentation and the decision records in the same change set.

## 4. Branches and releases

Branch from `dev` as `<type>/<topic>` and open pull requests into `dev`. `main` receives releases only, through
a pull request from `dev`. release-please (`.github/workflows/release-and-sync.yml`) cuts each release from `main`.
An agent pushes its branch or opens a pull request only when the owner asks. It never merges, tags or publishes a
release.

Commit messages follow Conventional Commits (`<type>(<scope>): <description>`); `.husky/commit-msg` runs
commitlint on each one.

## 5. How to write for people

These rules apply to chat replies, plans, reports, commit messages, pull request descriptions and docs.

- **Reader:** write for a new engineer who knows TypeScript and Node, but not this repository or its terms.
- **Bottom line first:** put the answer, the result or the decision you need in the first two lines.
- **Plain language:** short sentences (at most 25 words), active voice, one term per meaning.
- **Reports:** a status report says what is done, not done, blocked and next. A done report says what changed,
  how it was checked and what was not done.
- **Decisions:** give the context, two to four options with pros and cons, your recommendation and the default.

## 6. Never

- Never open, print, log or commit `.env` or any other secret store. Secrets go in `.env`; the variable names go
  in `.env.example`.
- Never commit or push to `main` or `dev`.
- Never edit `.github/workflows/` unless the task asks for it.
- Never skip, delete or weaken a test or a lint rule to get a gate green.
- Never ship a public method without a positive and a negative test.
- Never let a unit test touch the real filesystem, git or network. Inject a typed stub; do not mock whole modules.
- Never verify work with an ad-hoc command. Use the seven verbs in section 1.
- Never add a runtime dependency without an ADR that records the decision.
- Never describe a planned feature as if it exists.
