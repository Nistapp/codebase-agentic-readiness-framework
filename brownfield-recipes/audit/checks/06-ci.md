# Continuous Integration (`CI`)

> Follows the anatomy in [`README.md`](README.md). Four checks: `CI-01` to `CI-03` are `method:
> automated`; `CI-04` is `method: agent` (no engine ID). See
> [Why These Checks §7](../../deterministic-audit/docs/architecture/user-overview/03-why-these-checks.md#7-ci-ci)
> for the consequence behind this family: the gate an agent *can* run locally must be the gate that
> *decides*, or CI is a second, secret command surface nobody can reproduce.
>
> **The engine does not parse YAML.** `ci.py` is a minimal, documented text scan: it recognises
> `run:`/`script:`/`command:` steps, splits them on shell operators, and matches triggers by pattern —
> anchors, expressions, `uses:` steps and full YAML semantics are out of scope. Every `CI-*` check below
> is read against that scan, so an agent working this family reads the workflow files directly, for
> meaning, including the parts the scan cannot see: a reusable workflow called with `uses:
> ./.github/workflows/x.yml` whose own body defines the actual steps; a `strategy.matrix` that fans one
> job out into several, each with its own effective command; and a composite action (`uses:
> ./.github/actions/x`) whose `action.yml` holds the real `run:` steps. A finding that rests only on what
> the engine's text scan matched, when the workflow's real behaviour lives one level of indirection away,
> is not evidence — read the referenced file before trusting a `FAIL` or a `PASS` the scan produced on a
> workflow that uses any of these three forms.

---

## CI-01 — Pipeline present, triggered on PRs

Why it matters   Verification must be automatic and independent of the author, or "I ran the tests"
                  before pushing is unverifiable by anyone else
                  ([greenfield-bootstrap/README.md § 4.1 Workflows](../../../greenfield-bootstrap/README.md#41-workflows)).
Severity         BLOCKER
Engine           `CI-01`. Finds every workflow file the detected CI providers' globs name
                 (`audit.stack.CI_PROVIDERS`: GitHub `.github/workflows/*.yml(aml)`, GitLab
                 `.gitlab-ci.yml`, Jenkins `Jenkinsfile`, Azure `azure-pipelines.yml`, CircleCI
                 `.circleci/config.yml`, Buildkite `.buildkite/*.yml`) and tests each for a pull-request
                 trigger by a fixed pattern per provider (GitHub `pull_request`/`pull_request_target`,
                 GitLab `merge_request`, Azure `pr:`, Jenkins `changeRequest`). At least one workflow with
                 a matching trigger is `PASS`. Workflows exist but none match is `PARTIAL`. No workflow
                 file at all is `FAIL`. CircleCI and Buildkite have no local pattern at all — their PR
                 trigger lives in the platform's own VCS integration, not the checked-in file — so a
                 workflow on either provider can never earn `PASS` from this engine and should be verified
                 by reading the project's CI platform configuration directly, not the checked-in YAML.
Method           automated
Look for         The workflow file's trigger block itself (`on:`, `trigger:`, or the provider's own
                 keyword); for a reusable workflow invoked by `uses:`, read the caller's trigger, not the
                 reusable workflow's own (a reusable workflow has no trigger of its own to read).
Rubric           PASS: at least one workflow file exists and declares a pull-request trigger the engine's
                 pattern recognises.
                 PARTIAL: at least one workflow file exists but none declares a recognised pull-request
                 trigger.
                 FAIL: no CI workflow file exists at all.
                 NOT_APPLICABLE: never.
                 UNKNOWN when: never — the engine always reaches PASS, PARTIAL or FAIL for this check.
Evidence to cite A `file` evidence item per workflow file read, with `note` stating whether its trigger
                 block matched a pull-request pattern.
Absence proof    A FAIL cites the absence of every provider glob checked (a `glob` search per provider
                 with a `0` hit count); a PARTIAL cites every workflow file found and its trigger block as
                 the evidence that none matched.
Remediation      `add-ci-parity`
Pitfalls         CircleCI and Buildkite workflows are a real gap in this check's coverage, not proof the
                 project lacks a PR-triggered pipeline — read the project's CI platform settings (branch
                 protection rules, the VCS integration's own trigger configuration) before accepting a
                 `PARTIAL` on either provider as a true finding.

## CI-02 — Local↔CI parity

Why it matters   The gate an agent *can* run locally must be the gate that *decides*, or an agent
                  optimises against a weaker local gate and discovers the real gap only at review
                  ([greenfield-bootstrap/README.md § 1.4 The standardized command surface](../../../greenfield-bootstrap/README.md#14-the-standardized-command-surface--seven-verbs)).
Severity         BLOCKER
Engine           `CI-02`. Resolves the local framework verbs the same way `CMD-01` does
                 (`resolve_verbs`), then scans every workflow's `run:`/`script:`/`command:` steps for a
                 framework verb, by runner indirection (`npm run lint`, `make test`, `./gradlew check`,
                 `task typecheck`) or by a direct tool invocation the engine's pattern table maps to a
                 verb (`eslint` → `lint`, `mypy` → `typecheck`, `pytest` → `test`, and the rest). A CI verb
                 with no local definition is `FAIL`. A local read-only verb CI never exercises is reported
                 in `detail` but does not fail the check on its own — CI may legitimately delegate to the
                 composed `check` gate instead of calling each verb by name. No local verb resolves at all
                 is `UNKNOWN`. Distrust a `FAIL` when the "extra" CI command actually lives inside a
                 reusable workflow, a matrix leg, or a composite action the scan did not follow — read
                 that referenced file before accepting the gap as real; distrust a `PASS` the same way, in
                 case a matrix leg's own command is the one that actually diverges.
Method           automated
Look for         Every `run:`/`script:`/`command:` step across every workflow file, including the body of
                 any reusable workflow or composite action a `uses:` step calls and every leg a
                 `strategy.matrix` expands into; the local runner's resolved verb commands to compare
                 against.
Rubric           PASS: every framework verb a CI command invokes also resolves locally.
                 PARTIAL: not used by this check (the engine's outcome is binary: an extra CI verb with no
                 local definition is already FAIL).
                 FAIL: at least one CI command invokes a framework verb that resolves on no local runner.
                 NOT_APPLICABLE: never.
                 UNKNOWN when: no local verb resolves on any runner, so CI has nothing to be compared
                 against.
Evidence to cite A `command` evidence item per offending CI step, citing the workflow file, line and exact
                 command text, with `note` naming the verb it was mapped to.
Absence proof    A FAIL cites each offending command's workflow/line/text directly — the command is the
                 evidence of the gap, so no separate absence search applies; an UNKNOWN cites every runner
                 manifest checked with no verb resolving on any of them.
Remediation      `add-ci-parity`
Pitfalls         A verb CI exercises only inside a reusable workflow or a composite action is invisible to
                 the engine's own text scan of the caller's workflow file — read the referenced file
                 directly; crediting `PASS` from the caller alone, when the reusable workflow's own body
                 is where the divergence actually lives, is a false negative waiting to be found at
                 review.

## CI-03 — CI-only steps flagged

Why it matters   A step with no local equivalent is a failure an agent cannot reproduce, so it cannot
                  investigate or fix what CI is failing it on
                  ([greenfield-bootstrap/README.md § 1.4 The standardized command surface](../../../greenfield-bootstrap/README.md#14-the-standardized-command-surface--seven-verbs)).
Severity         DEGRADER
Engine           `CI-03`. For every CI command that is not already `CI-02`'s subject (it invokes no
                 framework verb), checks whether it names a runner target (`npm run <x>`, `make <x>`,
                 `task <x>`, `./gradlew <x>`) with no entry in the local runner manifest's own targets.
                 Package-manager plumbing (`npm ci`, `npm publish`, and the rest of a fixed built-in list)
                 and shell automation with no runner target (`gh`, `echo`, a bare `curl`) are not project
                 tools and are never flagged. No findings is `PASS`; any CI-only target found is `FAIL`.
                 Distrust a `FAIL` when the flagged target is actually defined inside a reusable workflow
                 or composite action the local manifest check did not expand — verify the target is truly
                 absent by reading the full set of runner manifests, including ones a monorepo workspace
                 might define per-package.
Method           automated
Look for         Every CI command's runner-target name, checked against every local runner manifest's own
                 target list, not just the primary one; a composite action's own `action.yml` for its
                 real steps, when the caller only names the action.
Rubric           PASS: no CI command names a runner target absent from every local runner manifest.
                 PARTIAL: not used by this check (the engine's outcome is binary: a CI-only step either
                 exists or it does not).
                 FAIL: at least one CI command names a runner target with no local definition.
                 NOT_APPLICABLE: never.
                 UNKNOWN when: never — absence of any CI-only step, including when no workflow exists at
                 all, is a real PASS.
Evidence to cite A `command` evidence item per CI-only step, citing the workflow file, line and command
                 text, with `note` naming the missing runner target.
Absence proof    A FAIL names each offending target and cites the command that invokes it; the absence of
                 a matching local target is itself what the finding asserts, so the cited command is the
                 proof, not a separate search.
Remediation      `add-ci-parity`
Pitfalls         A target that exists in a sub-package's own manifest (a monorepo workspace, a Gradle
                 module) but not the root one is a real local target, not a CI-only step — the engine
                 reads only the manifests `_common` resolves; check every workspace member's manifest
                 before trusting a `FAIL` here on a monorepo.

## CI-04 — CI enforces the same gate as the local check

Why it matters   A pipeline that runs the verbs but does not fail the build when one of them fails is
                  theatre, not enforcement
                  ([greenfield-bootstrap/README.md § 1.4 The standardized command surface](../../../greenfield-bootstrap/README.md#14-the-standardized-command-surface--seven-verbs)).
Severity         DEGRADER
Engine           none — telling "this step's exit code gates the job" from "this step runs but is
                 informational" needs reading the workflow's control flow (`continue-on-error:`, a step
                 whose failure is swallowed by `|| true` or an `if:` guard, a job with no required status
                 check wired to branch protection), which is not a pattern this engine's text scan
                 attempts; this is the second check in the catalogue with `method: agent` and no
                 `engine_id` (the first is `AGT-11`). Status in the catalogue was `planned` until this
                 rubric exists; this leaf makes it exist.
Method           agent
Look for         Every job that runs a `CI-02`-mapped verb (or the composed `check` gate), read for:
                 whether the step or job sets `continue-on-error: true`; whether the command itself
                 swallows its own exit code (`|| true`, `; exit 0`, a `set +e` with no later check); and,
                 separately from the workflow file, whether the repository's branch-protection settings
                 (not committed as YAML, so check the platform or ask the owner) actually require this
                 workflow's job to pass before a pull request can merge. For a reusable workflow, a
                 matrix leg, or a composite action, follow the same control-flow read into the referenced
                 file rather than stopping at the caller.
Rubric           PASS: every job running a verb (or `check`) gates on it — no `continue-on-error`, no
                 swallowed exit code on the gating command — and the workflow is a required status check
                 for merging (confirmed, not just assumed from the workflow file alone).
                 PARTIAL: the workflow file gates correctly but the required-status-check wiring could not
                 be confirmed, or one non-gating verb among several is swallowed while the rest genuinely
                 fail the build.
                 FAIL: a job's gating command's failure is swallowed (`continue-on-error`, `|| true`, or
                 equivalent) so the pipeline can report success on a change that actually failed a verb.
                 NOT_APPLICABLE: never.
                 UNKNOWN when: `CI-01` already reports no workflow exists, or no workflow runs a verb
                 (`CI-02`) at all, so there is no gate to judge.
Evidence to cite An `index_query` or `file` evidence item citing the workflow file and job, with `note`
                 stating what was read (the control-flow keyword found or absent, and the branch-
                 protection confirmation or its absence) for each job inspected.
Absence proof    A FAIL cites the exact line that swallows the command's failure (`continue-on-error:
                 true`, `|| true`, or the equivalent) as the evidence that the gate is not enforced.
Remediation      `add-ci-parity`
Pitfalls         A workflow that passes every verb genuinely but is not wired into the platform's required-
                 status-check list still fails to enforce anything — a human can merge past a red check —
                 so `PASS` needs the branch-protection confirmation, not just a clean read of the workflow
                 file; where that confirmation cannot be made (no access to the platform's settings),
                 `PARTIAL` is the honest verdict, not a `PASS` on the file alone.
