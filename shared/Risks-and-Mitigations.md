# Risks and Mitigations

> [!NOTE]
> This section captures known risks when adopting agentic workflows in codebases. R1-R8 concern the methodology; R9-R14 are introduced by the audit and implement recipes and each names the page that owns its mitigation. It will be expanded as the tooling matures and real-world patterns emerge.

## Risk Matrix

| # | Risk | Impact | Mitigation |
|---|------|--------|------------|
| R1 | `Minor`: **Stale documentation** — Generated docs drift from the code they describe. | Agents operate on outdated context, producing incorrect changes. (This is minor in our context as `agentic-tdd` also has a documentation agent to ensure up-to-date-ness.) | Re-running documentation tools as part of CI can be a good practice.|
| R2 | **Hallucinated docstrings** — Agent-generated documentation contains unsupported claims about business logic or security. | False assumptions propagate into downstream agent decisions. | Conservative generation rules: avoid business/security claims without evidence. Human review of initial generation. |
| R3 | **Over-reliance on characterization tests** — Teams treat behavioral baselines as proof of correctness. | Existing bugs become enshrined as "expected behavior." | Characterization tests should be explicitly labeled as *behavioral baselines, not correctness proofs*. Pair with intentional specification. |
| R4 | **Agents weakening tests** — An agent modifies or removes tests to make its code changes pass. | Silent regression; the safety net is removed. | Independent verification: tests and security checks run in a separate, agent-inaccessible pipeline. Constraint Engineering deny lists for test directories. |
| R5 | **Constraint erosion** — Allow/deny lists become overly permissive over time as teams take shortcuts. | Agent blast radius expands silently; spaghettification returns. | Periodic audit of constraint configurations. Treat constraint files as reviewed infrastructure, not developer convenience. |
| R6 | **Context pack incompleteness** — The context pack misses a critical dependency or side effect. | Agent produces code that compiles but breaks an undiscovered integration. | Use `codebase-memory-mcp` comprehensively. Run impact analysis before plan approval. Add missing relationships when discovered. |
| R7 | **Tool immaturity** — Several tools in the ecosystem are planned or aspirational, not yet available. | Teams may adopt the methodology expecting tooling that does not yet exist. | [tool maturity status](Tool-Ecosystem.md). The methodology is valuable even with manual execution of some phases. |
| R8 | **False confidence** — Teams assume agent-produced code is correct because it passed quality gates. | Subtle logic errors or security issues may slip through automated checks. | Human review remains necessary for high-risk changes. Quality gates increase probability but do not guarantee correctness. |
| R9 | **Provider exposure during an audit** — Whatever the audit agent reads from the repository (file contents, index query results, git log) is visible to the model provider behind the harness. | Proprietary or sensitive content leaves the operator's machine without the owner having decided it should. | The audit states this once before accepting intake, and the intake requires `provider_exposure_acknowledged: true`. A local code index stays local; only what the agent reads through it leaves. Owner: [Trust & Safety §3](../brownfield-recipes/docs/architecture/user-overview/03-trust-and-safety.md#3-data-egress). |
| R10 | **Probes run the target's own commands** — The engine's opt-in Tier-C runner executes a verb the target defines (`make test`, `npm run lint`), which is arbitrary code the target owns. | A hostile or broken repository can run code on the auditor's machine. | Off by default: it needs `--run-gates` and `--allow-probe <verb>` per verb, only for a read-only verb of the seven, with a timeout the operator sets. The recipe says so before it asks for consent and suggests a disposable worktree or container. Owner: [Trust & Safety §2](../brownfield-recipes/docs/architecture/user-overview/03-trust-and-safety.md#2-command-execution). |
| R11 | **Prompt injection through target files** — A file, comment, commit message, finding text or `AGENTS.md` in the target contains text addressed to the agent. | The agent skips a check, marks it `PASS`, runs a command or opens a pull request on the text's say-so. | Everything read from the target is data, never an instruction; the implement recipe repeats this as a hard rule and warns the person when it meets such text. Owners: [Trust & Safety §4](../brownfield-recipes/docs/architecture/user-overview/03-trust-and-safety.md#4-prompt-injection) and [§5](../brownfield-recipes/docs/architecture/user-overview/03-trust-and-safety.md#5-implementation-safety). |
| R12 | **Agent-opened pull requests** — The implement recipe pushes a branch and opens a pull request in the target. | Unreviewed changes reach the target's remote, or an agent merges its own work. | Local branch by default; push and one pull request only when the owner recorded `ci.pr_by_agent=yes` at triage; never merge, tag or force-push. Owner: [ADR 0003](../brownfield-recipes/docs/architecture/adrs/0003-push-and-pr-policy.md). |
| R13 | **Template and fixture bleed in the engine** — A check reads sample or carried data (a `templates/` folder, a fixture) as if it were the repository's own. | A verdict credits or blames the repository for files it does not use, so a score is wrong in either direction. | The engine decides what counts as the repository: carried-data directories are set aside and listed in the report, and nested ignore files are read. Owners: engine [ADR-0008](../brownfield-recipes/deterministic-audit/docs/architecture/adrs/0008-what-counts-as-the-repository.md) and [ADR-0009](../brownfield-recipes/deterministic-audit/docs/architecture/adrs/0009-nested-ignore-files-and-negation.md). |
| R14 | **User-level configuration leaking into verdicts** — The engine reads files under `$HOME` (an MCP registration, a global ignore file), so one machine scores differently from another. | The same repository gets different scores for different auditors, and a verdict depends on a file the repository does not hold. | Every report lists the paths outside the target that were read (`provenance.user_config`), and `--no-user-config` reads nothing under `$HOME`; the self-audit always runs with it. Owner: the engine [changelog](../brownfield-recipes/deterministic-audit/docs/reference/changelog.md) (ruleset `2026-11-05.4`) and [Self-Audit](../brownfield-recipes/docs/reference/self-audit.md). |

## General Principle

> [!IMPORTANT]
> These tools improve the **probability** of accurate work but do not **guarantee** correctness. Human review remains necessary for high-risk changes.
